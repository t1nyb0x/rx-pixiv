# ADR 0015: 管理コマンドと濫用対策を v1 に入れる

- Status: Accepted
- Date: 2026-08-10
- Issue: -

## Context

[Plan 0001](../../.claude/addf/plans/0001-requirements-and-adr.md) で確定した v1 設計には、
**運用者が Bot を制御する手段が一切無かった**。

- サーバーから抜ける手段が無い。招待された先が誤用しても、環境変数を変えて再デプロイするしかない
- 特定の利用者・サーバーを止める手段が無い
- [ADR 0014](0014-media-delivery-via-proxy-url.md) で「削除要請には速やかに応じる」と表明したが、
  **応じる仕組みが無い**。姿勢だけ表明して手段が無いのは、書いていないより悪い
- 利用者ごと・サーバーごとのクールダウンが無い

rx-twitter は DM の `!owner/...` コマンドで ban / unban / ban-guild / leave / list-bans /
guilds を持っており、実運用で機能している。rx-pixiv には対応物が無い。

なお [ADR 0014](0014-media-delivery-via-proxy-url.md) により**帯域増幅の懸念は消えた**
（Bot はバイトを運ばない）。しかし以下は残る。

- pixiv API のレート予算を食い潰される（[ADR 0011](0011-rate-limit-and-circuit-breaker.md) の
  トークンバケットは pixiv を守るが、待ち行列は伸びる）
- Bot のメッセージによるチャンネルの汚染
- 権利者からの削除要請に応じられない

## Decision

**管理コマンドと濫用対策を v1 のスコープに入れる。**

### 1. オーナー専用コマンド（DM プレフィックス方式）

rx-twitter に倣い、スラッシュコマンドではなく DM の `!owner/...` プレフィックスコマンドとする。
コマンド登録の運用（グローバル登録の反映待ち・権限設計）を持ち込まずに済むため。

| コマンド | 役割 |
|---|---|
| `!owner/guilds` | 導入サーバー一覧 |
| `!owner/leave <guildId>` | サーバーから離脱 |
| `!owner/ban <userId> [理由]` / `!owner/unban <userId>` | 利用者の禁止 |
| `!owner/ban-guild <guildId> [理由]` / `!owner/unban-guild <guildId>` | サーバーの禁止 |
| `!owner/list-bans` | 禁止一覧 |
| `!owner/block <artworkId\|user:<pixivUserId>> [理由]` / `!owner/unblock ...` | **展開拒否リスト**（削除要請の受け皿） |
| `!owner/list-blocks` | 展開拒否一覧 |
| `!owner/status` | サーキット状態・キャッシュ・レート消費の要約 |
| `!owner/help` | ヘルプ |

- 実行者は `OWNER_USER_ID` に一致する DM のみ。それ以外は無反応
- 出力は 1900 文字ごとに分割する

### 2. 展開拒否リスト（ブロックリスト）

**削除要請の受け皿である。** 再デプロイなしで更新できることが要件。

- 作品 ID 単位（`block:artwork:{id}`）と pixiv ユーザー ID 単位（`block:user:{id}`）の2粒度
- 一致した URL は**何も投稿せずスキップ**する（`skip` と同じ挙動。理由を info ログに残す）
- 判定は取得の**前**に行う。ブロック対象に対して pixiv へリクエストを飛ばさない

### 3. クールダウン

| 対象 | 既定 |
|---|---|
| 利用者ごと | 10秒に1メッセージ（`USER_COOLDOWN_MS`） |
| チャンネルごと | 5秒に1メッセージ（`CHANNEL_COOLDOWN_MS`） |

- 超過時は**無反応**（警告も出さない。警告自体が雑音であり、[ADR 0006](0006-age-restricted-content.md) の
  `skip` と同じ理由）
- オーナーはクールダウンの対象外

### 4. 判定の順序

`messageCreate` の先頭で、**安いものから順に**弾く。

```
1. Bot 自身・他 Bot          → 終了
2. オーナーコマンド（DM）     → 処理して終了
3. サーバー禁止 / 利用者禁止   → 終了
4. 許可チャンネル判定          → 終了
5. クールダウン               → 終了
6. URL 検出（ここで初めて本文を解析）
7. 展開拒否リスト             → 該当分をスキップ
8. 取得へ
```

禁止・クールダウンの判定を URL 検出より**前**に置く。
本文解析すら行わせないことで、濫用時の処理コストを最小にする。

## Consequences

### Positive

- 誤用しているサーバーから**即座に抜けられる**。再デプロイが要らない
- 削除要請に**実際に応じられる**。ADR 0014 の表明と仕組みが揃う
- pixiv API のレート予算が、特定の利用者に食い潰されない
- ブロック判定を取得前に置くことで、拒否対象への外部リクエストがゼロになる

### Negative

- v1 のスコープが増える（Plan が1本増える）
- 禁止・ブロックの状態は再起動をまたいで残る必要があり、
  **永続ストアが要る**（[ADR 0016](0016-redis-for-persistent-state.md) を引き込む）
- DM プレフィックスコマンドは Discord のネイティブな管理 UI ではないため、
  オーナー以外には使えない（意図的な制約でもある）
- `DirectMessages` intent と `Message` / `Channel` の partial が必要になる

### Mitigation

- 永続ストアの導入は [ADR 0016](0016-redis-for-persistent-state.md) で正面から扱う。
  ban が再起動で消えるなら ban の意味が無いため、ここは妥協しない
- コマンドは1ファイル（`OwnerCommandHandler`）に閉じ、
  パースとディスパッチだけを持つ薄い層にする。判定ロジックは `core/services/` に置く
- スラッシュコマンドへの移行は将来の選択肢として残す（本 ADR は塞がない）

## Rejected alternatives

### 管理面を持たず、環境変数だけで運用する

変更のたびに再起動が要る。誤用しているサーバーから抜けるのに再デプロイを要するのは、
**インシデント対応として遅すぎる**。削除要請にも応じられない。

### スラッシュコマンドで実装する

コマンド登録の反映待ち、ギルドごとの権限設計、`ApplicationCommand` の
デプロイ手順が増える。オーナー1人しか使わない管理面に見合わない。
rx-twitter が DM プレフィックス方式で実運用できている前例もある。

### クールダウン超過時に警告を返す

警告メッセージ自体がチャンネルの雑音であり、
連投されると**警告のほうがスパムになる**。無反応が正しい。

### ブロックリストを取得の後に判定する

拒否すると決めている作品に対して pixiv へリクエストを飛ばすことになる。
上流に対しても、レート予算に対しても無駄である。
