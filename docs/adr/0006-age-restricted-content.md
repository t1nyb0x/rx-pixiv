# ADR 0006: 年齢制限コンテンツはフェイルクローズで扱う

- Status: Accepted
- Date: 2026-08-10
- Issue: -

## Context

pixiv には R-18 / R-18G 作品が一般的に流通している。
URL のプレビューを補うということは、それらを不用意に展開しうるということでもある。

**この Bot で起こしうる最悪のバグは、R-18 画像が通常チャンネルに
インライン展開されることである。** サーバー運営者にとっては規約違反であり、
Discord にとっては通報対象であり、その場に居合わせた人にとっては単に害である。

判断を難しくする事情が3つある。

1. 年齢区分の確定には作品メタデータが要るが、**R-18 作品は無認証の Ajax API では
   取得できない可能性が高い**。つまり「危険なものほど情報が取れない」
2. Discord のスレッドは `nsfw` 属性を**持たない**。親チャンネルから継承する必要があり、
   ここは沈黙する偽陰性（危険なのに安全と判定する）の温床になる
3. DM には年齢制限属性という概念自体が無い

オーナーの方針は「**NSFW チャンネル限定＋スポイラー**」であり、
DM は「非 NSFW 扱い」と決まっている。

## Decision

### 1. 年齢区分を確信度つきでモデル化する

```ts
type RatingLevel      = "all" | "r18" | "r18g";
type RatingConfidence = "authoritative" | "inferred" | "unknown";

interface ContentRating {
  level: RatingLevel;
  sensitive: boolean;              // pixiv の sanity level >= 4。xRestrict とは別軸
  ai: "no" | "yes" | "unknown";
  confidence: RatingConfidence;
}
```

**`confidence` を持たない設計では本 ADR は実装できない。**
「年齢区分が分からない」を `undefined` ではなくドメインの一級の値として扱う。

| 経路 | 判定材料 | confidence |
|---|---|---|
| Ajax | `xRestrict`（0/1/2）、`sl`、`aiType`、タグ | `authoritative` |
| phixiv | `R-18` タグの有無 | `inferred` |
| OGP スクレイプ | 年齢確認インタースティシャルの検出 | `inferred` または `unknown` |
| いずれかが `auth_required` | **弾かれた事実そのもの** | `inferred` / level `r18` |

最後の行が要である。**無認証で弾かれたという事実は、
その作品が年齢制限されていることの証拠になる。**
これにより pixiv 認証がなくても本 ADR は成立する。
連鎖の後段は制限を**強める方向にしか**更新できない。

### 2. 判定表

`NsfwPolicy.decide({ rating, channelIsNsfw, isDM })` は4つの判定のいずれかを返す。

| 年齢区分 ＼ チャンネル | 年齢制限チャンネル | 通常チャンネル |
|---|---|---|
| `all`（センシティブでない） | `expand_plain` | `expand_plain` |
| `all` かつ `sensitive`（sl ≥ 4） | `expand_spoiler` | `expand_spoiler`（`SENSITIVE_IN_SFW` で調整可） |
| `r18` / `r18g` | `expand_spoiler` | **`link_only`** |
| `confidence: unknown` | `link_only` | **`skip`** |

### 3. `link_only` は本当にリンクだけにする

**タイトルもタグもサムネイルも作者名も出さない。** 定型文と正規 URL のみ。
R-18 作品は題名とタグ自体が露骨なことが多く、それらを通常チャンネルに流せば
画像を止めた意味が消える。Bot 自身の返信にも `SuppressEmbeds` を立て、
Discord 側にも展開させない。

### 4. `skip` は何も投稿しない

「Bot が展開を拒否した」という事実自体が情報の漏洩であり
（誰かが見せられないものを貼った、と分かってしまう）、かつ雑音である。
info レベルでログに記録するだけにする。

### 5. チャンネル判定

`isAgeRestricted(channel)` を1箇所に集約し、以下を扱う。

- `GuildText` / `GuildAnnouncement` / `GuildVoice` / `GuildStageVoice`: `.nsfw` を読む
- **スレッド（`PublicThread` / `PrivateThread` / `AnnouncementThread`）: `channel.parent?.nsfw` を読む**
- フォーラム投稿: フォーラムチャンネルから継承する
- **DM / グループ DM: 年齢制限チャンネルではないものとして扱う**（`ALLOW_NSFW_IN_DM` で変更可、既定 `false`）
- 未知・将来のチャンネル型: 年齢制限チャンネルではないものとして扱う

Discord の**全 `ChannelType` を網羅するテーブルテストを必須**とする。

### 6. ユーザープロフィールは作品ごとに判定する

プロフィール自体が全年齢でも、最近作に R-18 が混ざりうる。
サムネイルは**1枚ずつ**判定し、通常チャンネルで制限ありまたは判定不能なものは
そのサムネイルだけ落とす（カード全体を落とすのではない）。

## Consequences

### Positive

- pixiv 認証がなくても年齢ゲートが機能する。`auth_required` 自体が信号になるため
- 「分からない」が型に現れるので、フェイルクローズが実装漏れではなく既定動作になる
- `link_only` の内容を絞ることで、テキスト経由の漏洩も塞げる
- 判定が `NsfwPolicy` の純粋関数1つに集約され、全直積のテーブルテストで担保できる

### Negative

- **偽陽性が出る**。取得に失敗しただけの全年齢作品が、通常チャンネルで無反応になる
- 認証なしでは、年齢制限チャンネルでも R-18 が `link_only` に留まることが多くなり、
  オーナーの方針の利得が目減りする
- センシティブ（sl ≥ 4）判定は pixiv 側の基準に依存し、
  体感とずれることがある（全年齢作品が不必要にスポイラーになる）

### Mitigation

- 偽陽性は `pixiv_render_total{decision}` で計測する。
  `skip` の急増は年齢判定またはその上流の故障を意味するので、
  メトリクスのアラート対象にする
- 認証による改善余地は [ADR 0007](0007-pixiv-session-optional.md) に切り出す。
  未確定の事実（無認証で R-18 を叩いたときの応答形）を実測してから決める
- `SENSITIVE_IN_SFW` を環境変数として用意し、運用でしきい値を調整できるようにする
- **偽陽性（出るべきものが出ない）は許容し、偽陰性（出てはならないものが出る）は許容しない。**
  この非対称性が本 ADR の核である

## Rejected alternatives

### 判定不能なら展開する（フェイルオープン）

利便性は上がるが、「危険なものほど情報が取れない」という
本 ADR の Context の性質と正面から衝突する。
取得に失敗しやすいのはまさに R-18 作品であり、
フェイルオープンは「R-18 のときだけ規制が外れる」設計になる。

### 通常チャンネルでも常にスポイラー付きで展開する

Discord のスポイラーはクリックで誰でも解除できる。
年齢制限チャンネルという Discord 側の仕組みを迂回することになり、
サーバー運営者の意図を Bot が上書きしてしまう。

### `link_only` でタイトルとサムネイルを出す

「画像さえ出さなければよい」という発想だが、
R-18 作品はタイトルとタグ自体が露骨なことが多く、
サムネイルも pixiv 側でぼかされているとは限らない。実効性が無い。

### `skip` の代わりにエラーメッセージを投稿する

「この作品は展開できません」と出すと、
その場に「誰かが展開できないものを貼った」という情報が残る。
これ自体が漏洩であり、かつ雑音である。ログに残すだけでよい。

### スレッドの `nsfw` をそのまま読む

スレッドは `nsfw` 属性を持たない。`undefined` を falsy として扱うと
「年齢制限チャンネル内のスレッド」が通常チャンネル判定になり、
**安全側ではあるが利便性を大きく損なう**。逆に truthy 側へ倒すと危険。
親から継承するのが正しく、全 `ChannelType` のテストで担保する。
