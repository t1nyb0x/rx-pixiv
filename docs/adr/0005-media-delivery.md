# ADR 0005: 画像は Bot が取得して Discord 添付として再配信する

- Status: Accepted
- Date: 2026-08-10
- Issue: -

## Context

pixiv の画像 CDN `i.pximg.net` は `Referer: https://www.pixiv.net/` を要求する。
Discord の埋め込みプロキシはこのヘッダを付けられないため、
**`EmbedBuilder.setImage(生の pximg URL)` は描画されない**。
Components V2 の `MediaGalleryItem` に URL を載せても同じである。

これは rx-twitter（プロキシ API が返す URL をそのまま載せる）とも
rx-instagram（`og:image` の URL をそのまま `setImage` する）とも異なる、
pixiv 固有の壁である。

取りうる手段は3つ。

- **(a) 自前の画像プロキシサービスを公開する** — `Referer` を付けて再配信する HTTP サービス
- **(b) 公開プロキシに依存する** — `phixiv.net/i/...`、`pixiv.cat` 等
- **(c) Bot がバイトを取得し、Discord の添付としてアップロードする**

同時に、要件 FR-4 は「R-18 作品は年齢制限チャンネルでも**スポイラー付き**で展開する」
ことを求めている。この要件が手段の選択を強く縛る。

## Decision

**(c) を採用する。Bot 自身が `Referer` を付けて画像を取得し、
Discord の添付ファイルとしてアップロードする。**
Components V2 の `MediaGalleryItem` からは `attachment://<name>` で参照する。

### 付随する決定

- **サイズ変種のラダー**: `regular`（img-master 1200px）を第一候補とし、
  バイト予算を超えるなら `small`（540px）→ `thumb` と落とす
- **`original`（原寸）は取得しない**。v1 に限らず恒久的に
- **バイト上限はストリーミング中に強制する**。`content-length` の事前確認だけに頼らない
  （欠落も詐称もありうる。実際に守ってくれるのは読み出しバイト数のカウンタである）
- **表示枚数は既定4枚・上限10枚**（MediaGallery の item 上限）。
  200ページのマンガでも4枚に留め、「全 200 ページ中 4 ページを表示」と明記してリンクを添える
- **添付の総バイト予算はメッセージ全体で配分する**。ファイル単位ではない。
  上限はギルドのブーストティア由来の値 × 0.9（10%のヘッドルーム）
- `IMediaFetcher` はポートとして定義し、`{ kind: "bytes" } | { kind: "url" }` を返す。
  取得に失敗した場合に (b) のプロキシ URL へ縮退する余地を残す。
  ただし**通常経路でプロキシに依存しない**

## Consequences

### Positive

- **要件 FR-4 を素直に満たせる唯一の手段である**。
  添付は `SPOILER_` 接頭辞（v1 Embed）と `MediaGalleryItem.spoiler = true`（Components V2）で、
  Discord がネイティブに実装したぼかしとクリック展開が item 単位で効く
- 第三者サービスの可用性リスクを負わない。phixiv が落ちても画像表示は死なない
- `Referer` を含む取得の詳細を自分で制御できる。タイムアウト・バイト上限・
  同時実行数をすべて自前で決められる

### Negative

- **帯域が約2倍かかる**（下りで取得し、上りで Discord へ送る）。
  `regular` × 4枚で概ね 1〜5MB／展開
- Discord へのアップロード遅延が体感速度を支配する
- **権利上の姿勢が「ホットリンク」から「再配信」に変わる**。
  pixiv.cat が置かれているのと同じグレーゾーンに入る
- Discord CDN の URL は署名付きで失効するため、添付 URL のキャッシュは失効時刻の管理が要る

### Mitigation

- 帯域: 添付 CDN URL をキャッシュし、再貼り付けでは pximg への再取得を行わない。
  枚数上限と変種ラダーで1展開あたりのバイト数を抑える
- 権利: **`regular` サイズのみ**（原寸を再配信しない）、**4枚上限**、
  **常に作品ページへのリンクを併記**、削除要請には速やかに応じる。
  この姿勢は README にも明記する
- CDN 失効: TTL は URL の `ex` パラメータから導出する。
  脆いと分かった時点で添付 URL キャッシュ自体を落とす（最適化であって要件ではない）
- 遅延: 取得は同時4本まで並列化し、`sendTyping()` で待ちを可視化する

## Rejected alternatives

### (a) 自前の公開画像プロキシサービスを立てる

**推奨しない。**

- 公開ホスト名・TLS・Cloudflare Tunnel が必要になり、
  現状ゼロである外部公開面を新設することになる
- 悪用の的になる。URL を知った第三者が pximg 中継用の無料 CDN として使える。
  対策には失効付き署名 URL の仕組みが要り、それ自体が一つのサブシステムになる
- **そこまでやってもスポイラーができない**。
  プロキシ URL を `||...||` で囲むと展開そのものが止まり、
  「ぼかした画像」ではなく「ぼかしたリンク」になる

厳密に多い労力で、厳密に少ない機能。再検討するのは、
再アップロードの帯域が制約になったとき、または
うごイラ対応（[ADR 0012](0012-ugoira-out-of-scope.md)）で
どのみちメディアサービスが必要になったときである。

### (b) 公開プロキシ（phixiv / pixiv.cat）に画像配信を依存する

実装量は最小だが、

- **phixiv の本家は 2026-06 にアーカイブ済み**であり、
  恒常機能の中核を寿命の保証されないサービスに預けることになる
- pixiv.cat は単一障害点であり、ボットのバックエンドとしての大量利用を明確に歓迎していない
- (a) と同じくスポイラーができない

メタデータ取得の**フォールバック**としては使う（ADR 0003）が、画像配信は預けない。

### `original`（原寸）を配信する

原寸は 20MB を超えることがあり、無料枠の添付上限（10 MiB）を素通りで割る。
帯域と権利上の露出が最大になる一方、Discord 上の表示品質は `regular` とほとんど変わらない。
最も損の大きい選択である。

### `content-length` だけでバイト上限を守る

`content-length` は欠落することも、実体と異なることもある。
事前確認は「無駄な取得を始めない」ための最適化として有用だが、
**上限の強制はストリーミング中のカウンタで行う**。
