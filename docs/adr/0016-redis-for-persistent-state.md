# ADR 0016: 永続が要る状態のために Redis を導入する（ADR 0008 を置き換える）

- Status: Accepted
- Date: 2026-08-10
- Issue: -
- Supersedes: [ADR 0008](0008-in-memory-cache.md)

## Context

[ADR 0008](0008-in-memory-cache.md) は「v1 では Redis を導入せず、
プロセス内 TTL+LRU で足りる」と決めた。その根拠は

> 保持したいデータはすべて「消えても致命的でないキャッシュ」であり、共有相手もいない

だった。この前提が [ADR 0015](0015-admin-commands-and-abuse-control.md) で崩れた。

- **禁止（ban）が再起動で消えるなら、禁止の意味が無い。** 誤用しているサーバーを
  ban した直後にデプロイが走れば復活する
- **展開拒否リスト（削除要請の受け皿）が揮発するのは論外。**
  権利者に「対応した」と伝えた翌日に再発しうる
- クールダウンは揮発してよいが、禁止と同じ経路で扱えるなら分ける理由がない

つまり v1 に「**消えては困る状態**」が生まれた。ADR 0008 の前提は成立しない。

一方で、ADR 0008 が Redis を避けた副次的な理由
（コンテナが増える・障害モードが増える）は依然として正しい。
**すべてを Redis に載せる必要は無い。**

## Decision

**Redis を導入する。ただし「消えては困る状態」に限る。
作品メタデータのキャッシュはプロセス内 LRU のまま据え置く。**

### 配置

| データ | 置き場所 | 理由 |
|---|---|---|
| 禁止（利用者・サーバー） | **Redis** | 消えては困る |
| 展開拒否リスト（作品・pixiv ユーザー） | **Redis** | 消えては困る（削除要請の受け皿） |
| 返信マップ（元メッセージ → Bot 返信） | **Redis**（TTL 24h） | ADR 0008 で「許容する劣化」としていた再起動時の追従不能が、ついでに解消する |
| クールダウン | **Redis**（短 TTL） | 禁止と同じ経路に載る |
| 作品メタデータ | **プロセス内 TTL+LRU** | 高頻度・大量・消えても再取得すればよい。ネットワーク往復を挟む価値が無い |
| ネガティブキャッシュ | **プロセス内 TTL+LRU** | 同上 |
| サーキットブレーカ状態 | **プロセス内** | 単一インスタンス前提（[ADR 0011](0011-rate-limit-and-circuit-breaker.md)） |

キー規約は rx-twitter に倣い `app:<domain>:<id>:<field>` とする。

| キー | 型 / TTL |
|---|---|
| `app:ban:list` | Set（`user:{id}` / `guild:{id}` の索引） |
| `app:ban:user:{id}` / `app:ban:guild:{id}` | JSON（理由・日時・実行者）／無期限 |
| `app:block:list` | Set（`artwork:{id}` / `user:{id}` の索引） |
| `app:block:artwork:{id}` / `app:block:user:{id}` | JSON（理由・日時）／無期限 |
| `app:reply:{originMsgId}` | Set（返信ID）／24h |
| `app:reply-deleted:{originMsgId}` | 文字列（削除tombstone）／24h |
| `app:cooldown:user:{id}` / `app:cooldown:channel:{id}` | 文字列／秒単位 TTL |

### Redis が落ちたときの縮退

**フェイルクローズを Redis にも適用する。** 判断の材料が取れないなら、動かないほうを選ぶ。

| 状態 | 挙動 |
|---|---|
| 禁止・展開拒否を**読めない** | **展開しない**（`REDIS_DOWN_FALLBACK=deny` が既定） |
| クールダウンを読めない | クールダウン無しとして通す（安全側の判断に影響しないため） |
| 返信マップを書けない | 展開は続行する。追従削除だけ諦める |

`REDIS_DOWN_FALLBACK=allow` で緩められるようにするが、**既定は `deny`**。
[ADR 0006](0006-age-restricted-content.md) の「偽陽性は許容し、偽陰性は許容しない」を
ここでも貫く。ban できていない状態で動き続けるより、止まるほうがよい。

起動時に Redis へ接続できない場合は**警告を出して起動を続ける**（Discord 接続は行う）。
`/readyz` は 503 を返し続ける。

### 起動時のプリロード

禁止と展開拒否は件数が小さく、変更頻度も低い。
**起動時に全件をプロセス内へ読み込み、変更時に更新する**。
ban/block照合では毎メッセージRedisへ往復しない。cooldownとreply mapは短TTLの
整合性が必要なためRedisを使う。

## Consequences

### Positive

- 禁止と展開拒否が再起動をまたいで生き残る。管理コマンドが実際に機能する
- ADR 0008 で「許容する劣化」としていた返信マップの消失が、ついでに解消する
- ギルド別設定・ダッシュボード連携（[Plan 0010](../../.claude/addf/plans/0010-guild-config.md)）や
  2インスタンス化への道が開く。`IWorkCache` を非同期にしておいた判断が活きる
- rx-twitter と Redis の運用手順が揃う

### Negative

- **コンテナが1つ増える**。docker-compose に redis サービスが必要になる
- 障害モードが1つ増える。Redis の停止という分岐を設計・実装・テストしなければならない
- `REDIS_DOWN_FALLBACK=deny` が既定なので、**Redis が落ちると Bot が実質停止する**
- ADR 0008 で「利用者から見た利得はゼロ」と書いた導入コストを、実際に払うことになる

### Mitigation

- 載せるのは「消えては困る状態」だけに限る。作品メタデータのキャッシュは
  プロセス内 LRU のまま据え置き、Redis をホットパスから外す
- 起動時プリロードにより、通常運用でban/block照合のRedis往復は発生しない。
  切断を検知したら古いpreloadを信用せず、既定denyでは再接続・再preloadまで展開を止める
- Redis の状態を `/health` と `/readyz` に出す
- `appendonly yes` で永続化する。展開拒否リストの消失は許容できない

## Rejected alternatives

### ADR 0008 を維持し、禁止・展開拒否もプロセス内に持つ

再起動で消える ban は ban ではない。削除要請への対応が揮発するのは、
[ADR 0014](0014-media-delivery-via-proxy-url.md) で表明した姿勢に反する。

### JSON ファイルで永続化する

単一インスタンスなら成立し、コンテナも増えない。実際、これでも要件は満たせる。

採用しない理由は、**同時書き込みの扱いと破損時の復旧を自前で設計することになる**点、
および [Plan 0010](../../.claude/addf/plans/0010-guild-config.md)（ギルド別設定・
ダッシュボード連携）へ進むとき、どのみち Redis へ移行して二度手間になる点。
rx-twitter で Redis の運用実績があることも判断材料に含めた。

**ただしこれは僅差の選択である。** コンテナを増やしたくない事情が生じたら、
ファイル方式へ戻す余地は残る（`IBanRepository` / `IBlockRepository` を
`core/ports/` に置き、実装を差し替え可能にしておく）。

### すべての状態を Redis に載せる（rx-twitter 方式）

作品メタデータのキャッシュは高頻度・大量であり、
ネットワーク往復を挟む価値が無い。プロセス内 LRU のほうが速く、Redis の負荷も減る。
ADR 0008 のこの判断は正しかったので維持する。

### Redis 停止時に `allow` で通す

禁止できていない状態で動き続けることになる。
展開拒否リストを読めないまま展開するのは、削除要請に応じていないのと同じである。
既定は `deny` とする。
