# ADR 0011: レート制御とサーキットブレーカで上流障害を局所化する

- Status: Accepted
- Date: 2026-08-10
- Issue: -

## Context

pixiv はアクセス頻度に対して厳しく、ボット対策も持つ。
一方 rx-instagram には、**タイムアウト・リトライ・同時実行制限・レート制御が
いずれも存在しない**。`Promise.all` で URL 数ぶんの取得を無制限に並列発火し、
`AbortController` も無いため、応答しない上流に対して無限に待つ。

rx-pixiv で同じことをすると、pixiv 側からの遮断を最短距離で引き当てる。
とくに以下の状況が危ない。

- 1メッセージに20本の作品 URL が貼られる（貼り爆撃）
- 複数ページ作品で、ページ数ぶんの画像を同時取得する
- 上流が 5xx を返し続けているのに、メッセージごとに毎回3経路を試して待つ
- レート制限（429）を受けたのにリトライして、さらに叩く

また、[ADR 0003](0003-source-fallback-chain.md) の3段フォールバックは、
死んだ経路があると**メッセージごとにその経路のタイムアウトぶん待つ**という
コストを持つ。phixiv の本家がアーカイブ済みである以上、これは絵空事ではない。

## Decision

4つの機構を組み合わせて、上流の障害を局所化する。

### 1. ホスト別トークンバケット

| ホスト | 持続 | バースト | 同時 |
|---|---|---|---|
| `www.pixiv.net` | 1 rps | 3 | - |
| `i.pximg.net` | 8 rps | - | 4 |

画像 CDN は API よりはるかに寛容なので、別枠にする。
[ADR 0007](0007-pixiv-session-optional.md) の認証が有効なときは
`www.pixiv.net` 側をさらに厳しくする（無認証で遮断されて失うのは IP だが、
認証済みで目を付けられて失うのはアカウントである）。

### 2. 経路別サーキットブレーカ

- 60秒以内に5連続失敗で**開**
- 開いている間（120秒）は `unsupported{reason:"circuit_open"}` を**遅延ゼロで**返す
- 120秒後に**半開**とし、1本だけ通して成否を見る

死んだ経路が、メッセージごとに3秒ずつ課金してくるのを止めるための機構である。

### 3. リトライ方針

| 事象 | リトライ |
|---|---|
| `network`（DNS / ECONNRESET） | 1回（250ms + ジッタ） |
| `upstream_5xx` | 1回（250ms + ジッタ） |
| `timeout` | **しない**（時間予算を既に使い切っている） |
| `rate_limited`（429） | **しない**（サーキットを開いて経路ごと降りる） |
| 4xx 全般 | しない |

**リトライは経路あたり最大1回。** レート制限をかけてくる相手に対して
リトライを重ねるのは、IP 遮断への最短経路である。

### 4. 同時実行の上限

| 対象 | 上限 |
|---|---|
| 1メッセージあたりの URL 数 | 3（超過分は件数のみ注記） |
| 1メッセージあたりの取得同時実行 | 2 |
| 1作品あたりの画像同時取得 | 4（かつ総バイト予算の下で） |

## Consequences

### Positive

- 貼り爆撃が上流への負荷にならない
- 死んだ経路のコストが、サーキットが開いたあとはゼロになる
- 429 を受けたときに事態を悪化させない
- レイテンシの最悪値が予測可能になる（時間予算 8 秒で固定）

### Negative

- 機構が4つ増える。実装量とテスト量が増える
- サーキットが開いている間は、実際には復旧している経路も使われない（最大120秒）
- レート制限により、同時に多数のメッセージが来ると待ち行列ができる

### Mitigation

- 4機構はいずれも `infrastructure/http/` の小さな独立クラスとし、
  フェイクタイマーで単体テストする。ライブラリは導入しない
- 半開（120秒後に1本通す）により、復旧の検知は自動で行われる
- `pixiv_circuit_state{source}` をメトリクスに出し、開きっぱなしを検知できるようにする
- 待ち行列は時間予算で打ち切られる。無限に伸びない

## Rejected alternatives

### 何も入れない（rx-instagram 方式）

pixiv のレート制限とボット対策を考えれば、遮断されるまでの時間の問題でしかない。
また、応答しない上流に対して無限に待つ実装は、
Discord 側のメッセージ処理を詰まらせる。

### 指数バックオフで粘り強くリトライする

一般には正しいが、相手がレート制限をかけている場合は逆効果である。
「粘る」は「叩き続ける」と同義になる。
本 ADR では**リトライ1回・429 では即降参**を選ぶ。

### サーキットブレーカを入れず、タイムアウトだけで凌ぐ

死んだ経路がメッセージごとに3秒課金してくる。
3経路のうち2つが死ぬと、全メッセージが6秒遅くなる。
phixiv の本家がアーカイブ済みである以上、これは想定すべき事態である。

### ライブラリ（`bottleneck`・`opossum` 等）を使う

必要なのはトークンバケットとサーキットブレーカのそれぞれ数十行である。
依存を2つ増やし、その設定方法という学習対象を持ち込む価値がない。
フェイクタイマーでのテストも自前実装のほうが素直に書ける。
