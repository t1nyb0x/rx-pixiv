# 設計フェーズの3つの型

> 出典: rx-pixiv Plan 0001（要件定義・アーキテクチャ設計・ADR 整備）。
> コードを書かず、要件定義・設計書・ADR 13本・実装 Plan 10本を作るタスクで得た知見

## 発見した知見

### 1. 設計フェーズでも外部 API は実測する — 推測1つで一次経路の選定が変わる

pixiv の R-18 作品は無認証で取得できないという前提から設計に入ったが、
設計エージェントを起動する**前に** WebFetch で実際に叩いたところ、
v1 スコープの3種別（イラスト／小説／ユーザー）すべてが
無認証の公式 Ajax API で取得できることが分かった。

この1点で「一次経路を公式 API に据える」という中核の判断が決まった。
実測していなければ、公開プロキシ（phixiv）を一次に据える設計になっていた
可能性が高い。そのプロキシは本家が2026-06にアーカイブ済みで、
中核に置くべきではないサービスだった。

**実測は「設計を検証する」ためではなく「設計エージェントに渡す前提を正しくする」ために行う。**
前提が間違っていると、提案の質がいくら高くても出力は間違う。

### 2. 決めない箇所は ADR の `Status: Proposed` として明示的に残す

13本の ADR のうち1本（pixiv 認証の要否）だけを `Proposed` で残した。
決定に必要な事実（無認証で R-18 を叩いたときの応答形）を実測していなかったため。

`Proposed` の ADR には以下を書く:

- **何が分かれば決まるか**（「未確定の事実」節）
- **分岐したときそれぞれどうなるか**（区別できる場合／できない場合の帰結）
- **決定ログ**（起票日と、いつ何を待っているか）

こう書いておくと、**後続 Plan の完了条件がそのまま書ける**
（「スパイク結果が ADR 0007 の Context と決定ログに記録され、Status が確定している」）。

すべてを `Accepted` で埋めきろうとすると、いちばん危険な箇所
（この案件では年齢ゲートの縮退経路）が推測の上に建つ。

### 3. Plan 番号と ADR 番号は別採番なので、必ずプレフィックスを付けて書く

ドキュメントレビューで検出された指摘5件のうち**4件が Plan 番号の誤参照**だった。

| 誤記 | 正 |
|---|---|
| 「Plan 0004 のスパイク」（3箇所） | Plan 0005 |
| 「Plan 0001」（許可リストの判断） | Plan 0002 |
| 「Plan 0001 の時点で lint を入れる」 | Plan 0002（0001 には `package.json` すら無い） |
| 「Plan 0006 が `IMediaFetcher` を定義」 | Plan 0003 が定義、0006 は具象実装のみ |

原因は、Plan 番号と ADR 番号が**別の採番体系で偶然一致する**こと
（Plan 0007 = レンダリング配線、ADR 0007 = pixiv 認証）。
執筆中に頭の中で番号だけが残り、どちらの体系か取り違える。

**対策**: 文中では常に「Plan NNNN」「ADR NNNN」とプレフィックスを省略しない。
加えて、**設計フェーズの成果物には必ずドキュメントレビューを通す**。
数値整合（枚数・タイムアウト・カバレッジ閾値・TTL・レート制限）や
リンク切れは1件も検出されなかったのに対し、
相互参照の誤りは人間の目でもレビューエージェントでも
「読めば分かるが書いているときは気づかない」種類の欠陥だった。

## 適用条件

- コードを書かず設計文書だけを作る Plan（骨格プランニング、要件定義フェーズ）
- 外部 API に依存するプロジェクトの初期設計
- ADR と Plan の両方を採番して運用しているプロジェクト
